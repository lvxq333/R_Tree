### 0.1 D13 的收缩口径

原 13 序列方案里的「Java 六层 / 数据分析五层 / 销售双路径」全部作废，改为直接采用库内既有的三序列。三条序列的层级代码、层级名称、既有技能要求**原样保留**，不在草稿里另造名称：

| 序列 | T1 | T2 | T3 | T4 |
|---|---|---|---|---|
| `software` | 初级软件开发工程师 | 中级软件开发工程师 | 高级软件开发工程师 | 资深 / 专家工程师 |
| `platform` | **初级平台工程师** | 平台开发工程师 | 高级平台工程师 | 平台架构专家 |
| `ai` | **初级 AI 工程师** | AI 应用开发工程师 | 高级 AI 工程师 | AI 架构专家 |

三条序列原本 T1 都叫「初级软件开发工程师」，页面上无法区分，已改为按序列命名（008 迁移同步 `career_node.title`，slug 不变，`career_node_skill` 引用不受影响）。

技能矩阵的口径：

1. **沿用「每层只写本层新增或提高的要求」**，不改累积式。库内 `career_node_skill` 就是这个语义，确认稿的 Gap 例子（「L2→L3 额外要求五项能力」）也是这个语义，判断层取本层要求减去已满足项即为 Gap。
2. **每层固定 4 项**：48 条要求（3 序列 × 4 层 × 4 项）全部原样保留，不新增、不调等级。
3. **等级与层级的匹配先不较真**：T3 出现 L3、T4 出现 L5 都按既有数据保留，MVP 只保证流程闭环可验证；项目版本正式确定后再逐条校准。相应地，判断层**不得对「等级是否随层级递进」做硬校验**，否则校准时会全部报错。

`management`（管理通道）在库内存在，但**不纳入 MVP 的职称判定**：管理序列会和专业序列重复计入同一批员工，跨级判断会算错。

### 0.2 已化解的原始矛盾（v1.0 提出，现已关闭）

| 原编号 | 矛盾/风险 | 关闭方式 |
|---|---|---|
| H1 | 职称层数（确认稿 6/5 层 vs schema 4 层） | D13 + D1：只保留库内三序列，各 4 层，结构不写死 |
| H2 | 两套开发计划并存 | D2：确认稿为主线 |
| R1 | `deepseek-flash` 疑似无效模型名 | D8：实测该端点为网关，支持 `deepseek-flash` / `deepseek-v4-pro`，原判断不成立，沿用 flash |
| R2 | legacy-sync 不存在、双轨并行 | D3：单向双写 P0/P1 |
| R3 | 标准数据量过大 | D13 + D4：序列 13 → 3，全部精编，不新增技能 |

### 0.3 实现红线（不是待确认项，是 M7 必查项）

1. **版本快照单一入口**：判断层、AI 出题、审批展示一律走 `StandardSnapshotService`，禁止直读活动标准表。
2. **防作弊边界文档化**：页面上标注「本场考试按浏览器可检测行为记录离开次数」。
3. **双写失败隔离**：同步异常只写 `mvp_fact_sync_log`，不回滚认证结果。
4. **AI 失败即待重试**：模型超时/格式错误显示「待重试」，不计业务驳回。
5. **临时证据权限到期自动回收**：授权记录带 `expires_at`，任务结束即关闭。

## 1. 系统范围与页面基线

### 1.1 三层职责

```
事实中心侧（模拟接口 + 现有 facts 模块）     判断层（新增 judging）            技能树应用

└─ 评估结果持久化                        └─ 学习资源推荐                    └─ 旧页：认证数据贯通
```

## 2. 详细开发内容

### 2.1 数据层（M1）

**已就绪**：006 迁移 27 张 mvp 表（含 CHECK）。

**要做**：

1. **schema 修正**
   - `mvp_title_level.level_order`：去掉 `<= 4` 的 CHECK，保留 1~6 上限（D1）；
   - `mvp_appeal` 增 `decided_kind`（`ai`/`manager`/`expert`）；
   - `mvp_standard_version` 增 `source`（`refined`/`ai-draft`/`assumed`）、`reviewed_by`、`published_by`。
2. **Drizzle 定义**：补齐 `server/database/mvp-schema.ts`，独立于旧 `schema.ts`。
3. **种子脚本** `scripts/seed-mvp-standards.mjs`
   - 3 序列 × 4 层职称（`software` / `platform` / `ai`，全部精编）；
   - 职称技能要求 48 条（每层 4 项，增量语义），全部来自库内既有数据；
   - 子能力库 21 项（12 通用 + 9 序列专业），按技能分类挂载，不逐技能展开；
   - 81 项技能中 34 项进职称要求，其余留在技能池供自主认证；
   - 旧 domain 归一：`java`/`frontend`/`python`/`testing` → `software`，`devops` → `platform`，`data-*` → `ai`；`product` / `sales` 的 7 名演示员工改岗或标注超出范围；
   - 标准版本 `v2026-q4`，走三级发布生成 snapshot（D11）；
   - 4 真实 + 26 虚构员工、组织关系（主管/专家/专家组）、演示事实。
4. **历史数据迁移**：备份 → 旧等级直接映射进 `mvp_employee_skill` / `mvp_employee_competency`，标 `migrated`；无法对应的只留历史（D12）。

### 2.2 后端模块（M2~M5）

| 模块 | 核心能力 | 规则要点 |
|---|---|---|
| `standards` | 版本 CRUD、三级发布、snapshot、职称/子能力/流程配置、AI 建议采纳 | 草稿→负责人审核→管理员发布；AI 建议只进草稿；申请锁提交版本 |
| `judging` | 资格、进度、Gap、职称资格；事实事件触发重算 | 三状态区分；高等级满足低等级；同证据不重复累计；跨级按目标路径最高认证判断 |
| `application` | 草稿/提交/补材料/退回重提；逐项 AI 评估 | 材料按子能力关联；正式提交不可撤回；禁同等级重申（D10）；驳回 15 天冷却 |
| `exam` | 出题、开始、心跳、恢复、提交、评分、补考 | 5 题 100 分 80 及格；60 分钟；离开两次终止；5 分钟恢复；24h 补考（演示可跳）；已过项复用 |
| `approval` | L3 主管 / L4 +专家 / L5 +专家组全员；跨级加独立专家 | 专家组每人一行；冲突或缺失 → 待分配；通过后子能力可复用 |
| `appeal` | ≤2 次；AI 重判（L1L2 材料）→ 主管判；L3-L5 原驳回人→未参与专家；L2 考题异议独立入口 | 沿用原规则版本；申诉期禁建同目标 |
| `recertification` | 1 年无实践扫描 → 待复核 → 分类复核 → 解除或保留 | 不自动降级；新证据可解除；暂停/降级/撤销留痕并重算 |
| `notification` | 两类候选、冷却、流程通知、飞书接口 | 已读/处理中不重复推；复用 candidate-discovery |
| `fact-adapter` | 统一事实接口、增量 1 分钟 + 手动、幂等 | 不可用显示数据更新时间 |
| `file` | 上传、文本抽取、权限化访问 | 本机受控目录，20MB 白名单 |
| `legacy-sync` | P0/P1 单向映射（employee_skill / approval / skill_event / skill_gap / talent_candidate） | 失败记日志，可重推 |

## 4. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
